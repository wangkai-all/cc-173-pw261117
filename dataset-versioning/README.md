# 数据集版本管理工具

带**分支**与**字段级三方合并**的数据集管理工具。所有操作在网页完成；数据存为本地表（SQLite）与**不可变版本**，旧版本永远可查询。

## 启动

```bash
node server.js          # 打开 http://localhost:8080
node test/smoke.mjs     # 端到端冒烟测试（独立临时库，38 项断言）
```

零 npm 依赖（Node ≥ 22，使用内置 `node:sqlite` / `node:http`）。数据落在 `data/dataset.db`，**刷新或重启后分支、草稿、合并进度全部保留**。

## 核心概念

| 概念 | 说明 |
|---|---|
| 版本 | 每次发布生成不可变快照（`versions` + `version_rows`），有序号 v1/v2/…、父版本（合并版本有两个）、变更统计 |
| 分支 | 从任意版本开出；工作区 = head 版本 + 未发布草稿 |
| 草稿 | 分支上的追加/修改/删除先存草稿（`drafts` 表），可随时放弃或发布 |
| 三方合并 | 自动找共同祖先版本，按**字段**比对两边改动 |
| 合并会话 | 预览结果与逐项冲突解决进度落库（`merge_sessions`），可取消、可跨刷新续作 |

## 合并规则

- 仅一边改动的字段 → 直接合入
- 两边改了**不同字段** → 自动合并（**绝不整行互相覆盖**）
- 两边把**同一字段改成不同值** → 冲突，页面逐项选择（目标/源/自定义值）
- 一边删除、另一边修改 → 冲突，页面选择「保留修改」或「删除」
- 两边新增同一主键且内容不同 → 冲突，逐字段处理
- 合并前展示：新增 / 删除 / 自动合并 / 冲突 四类结果，确认发布才形成新版本

## 乐观并发（两人基于同一目标版本提交）

- 发布草稿：携带 `expected_head`，分支 head 已被别人推进 → `409`，工作区按新 head 重新比对后需再次确认
- 发布合并：目标（或源）分支 head 在会话期间被推进 → `409`，预览按最新状态**自动重算**、保留仍适用的解决方案、标记「需重新核对」，核对后才能发布 —— **不会悄悄覆盖先提交的内容**

## 演示脚本（订单数据）

初始为 `main` 分支 + v1（14 张订单）。

1. **开分支**：分支页 → 新建分支 `客服组`（基于 v1）；再建 `运营组`（基于 v1）
2. **分支编辑**：进入 `客服组` 工作区
   - 编辑 `SO-1003` 状态 → `已送达`；编辑 `SO-1004` 数量 → 5
   - 删除 `SO-1009`；新增 `SO-2001`
   - （修改实时落草稿，可刷新页面验证不丢失）
3. 进入 `运营组` 工作区
   - 编辑 `SO-1003` 状态 → `已取消`（与客服组冲突）
   - 编辑 `SO-1004` 区域 → `华北`（不同字段，将自动合并）
   - 删除 `SO-1006`；编辑 `SO-1009` 数量 → 3（与客服组的删除冲突）；新增 `SO-2002`
4. **三方合并**：在 `客服组` 工作区点「合并分支…」→ 源 `运营组` → 目标 `客服组`
   - 预览展示：冲突 2（SO-1003 字段冲突、SO-1009 删除/修改冲突）、自动合并 1（SO-1004 数量取客服组、区域取运营组）、新增 2、删除 1
   - 逐项解决冲突（选择取值即时保存，刷新后进度仍在）
   - 「取消合并」可随时放弃；重新发起会重算预览
5. **发布**：冲突清零后「发布合并」→ 生成新版本（两个父版本），`客服组` 草稿清空；旧版本在「版本」页仍可查询
6. **两人同时提交**（开两个浏览器窗口演示）：
   - 窗口 A 发起 `客服组 → 运营组` 的合并（先不发布）
   - 窗口 B 在 `运营组` 直接发布一笔修改
   - 窗口 A 再发布合并 → 被拒绝并提示「目标分支已推进，请重新核对」，预览自动重算；核对后发布成功，B 的内容完好

## 目录结构

```
server.js   HTTP 服务 + JSON API + 静态页面
db.js       SQLite 表结构与订单种子数据
merge.js    共同祖先查找 + 字段级三方合并 + 结果物化
public/     单页应用（分支 / 工作区 / 合并 / 版本四个视图）
test/smoke.mjs  端到端测试（38 项断言）
```
